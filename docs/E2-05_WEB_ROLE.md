## 1. Что именно получает web

Единый исполняемый перечень — `backend/tools/account_web_grants.py`. Производственная beta-роль только `mw_beta_web`; её проверочный аналог только `mw_beta_test_e2_05_web_v2`. Произвольное имя, production и дополнительные привилегии отвергаются. Новых зависимостей, RLS/Grant/RBAC или бизнес-ролей не добавлено.

| Таблица | INSERT — точные колонки | UPDATE — точные колонки | DELETE |
| --- | --- | --- | --- |
| ownership_user | id, created_at, archived_at, password, last_login, username, is_active | password, last_login | Нет |
| ownership_organization | Нет | id, только для row lock, изменение запрещено триггером | Нет |
| ownership_membership | id, created_at, archived_at, organization_id, user_id, role, state | id, только для row lock, изменение запрещено триггером | Нет |
| accounts_accountcontact | user_id, email, activated_at | activated_at | Нет |
| accounts_invitation | id, membership_id, scope_digest, token_hash, created_at, expires_at, used_at, revoked_at | used_at, revoked_at | Нет |
| accounts_attemptbucket | key, window_start, attempts | window_start, attempts | Нет |
| accounts_authdenial | occurred_at, kind | Нет | Нет |
| django_session | session_key, session_data, expire_date | session_data, expire_date | Да, для штатного flush/cycle/logout |

Обязателен SELECT на этих восьми таблицах и django_migrations. В главной beta существующее SELECT/default SELECT сохраняется, не заменяется новым глобальным правилом. В C1 SELECT выдаётся явно только этому списку. Скрипт не выдаёт blanket INSERT/UPDATE, GRANT OPTION, TRUNCATE, TRIGGER, MAINTAIN, REFERENCES, schema/DB CREATE, членство в миграторе или административные атрибуты. Контракт проверяет отсутствие неожиданного DML по **всем** public-таблицам/колонкам, отсутствие владения объектами/наследования ролей и CONNECT к другим доступным БД собственного экземпляра. Имеющиеся более широкие права приводят к отказу, а не к молчаливому отзыву чужих настроек.

Для audit.id используется Django 5.2 `GENERATED BY DEFAULT AS IDENTITY`; явный INSERT id не выдаётся. Sequence grants не добавляются: генерация identity проверяется HTTP-отказом, который пишет AuthDenial. Если конкретный PostgreSQL это не подтвердит, C1 должен остановиться, а не автоматически расширить права. Изменение типа identity также блокирует apply.

PostgreSQL требует UPDATE хотя бы одной колонки для `SELECT FOR UPDATE`. Поэтому в той же транзакции с GRANT создаются `public.accounts_web_lock_only()` (SECURITY INVOKER) и одноимённые BEFORE UPDATE OF id триггеры на Organization/Membership. Они запрещают даже `SET id=id` **только целевой web-роли**; row locks разрешены. У migrator/оператора поведение E2-04 остаётся прежним. Это два явных SQL-ограничения прав процесса, не изменение полей/связей или истории модели владения; миграции ownership не меняются. Guard-объекты относятся к применению/откату privilege contract, а не к model migrations.

Web не получает UPDATE User.is_active/archived_at/username или Membership.role/state/user_id/organization_id. Операторская блокировка выполняется отдельно доверенным процессом; использовать migrator как web запрещено. INSERT членства всё ещё технически позволяет записать разные роли/организации через доверенный SQL-процесс: полномочия пользователя контролирует сервис E2-05. Этот набор SQL-grants **не обещает изоляцию при произвольном SQL/компрометации приложения**, полноценный RBAC/RLS остаётся будущей задачей.

Посмотреть точный SQL без Django setup/секретов/подключения (из backend):

```powershell
.venv/Scripts/python.exe -m tools.manage_account_web_grants plan
```

Вывод — для ревью, не для исполнения через psql. `apply` и `revoke` выполняются только guarded module: проверка точных beta/migrate/host/database/user, session_user/current_user, обязательных миграций; одна транзакция; проверка ACL/guard до и после. Повторный apply откажет при существующих guards. Revoke откажет при расширившихся правах или изменившемся теле/привязке trigger; поздние изменения не стираются. Первоначальные SELECT сохраняются.

Затем **переподключает Django под настоящим LOGIN session_user=current_user=ограниченная роль**, а не SET ROLE из владельца. Только callback операторской блокировки временно использует отдельное runner-подключение, после него HTTP снова идёт ограниченной ролью. Пароли/токены/cookies/outbox не выводятся.

Это проверка HTTP-обработки и реальных SQL-привилегий, **не сетевой Gunicorn/TLS/браузерный тест**. Дополнительно отдельное соединение ограниченной роли проверяет SQLSTATE 42501 для persistent/temp DDL, UPDATE идентичности/роли/состояния, чужих таблиц и migration records, DELETE пользователей, TRUNCATE, SET ROLE runner/bootstrap. RESET ROLE остаётся ограниченной ролью. Отрицательные записи находятся в savepoint и откатываются даже при неожиданном успехе. Запрет CONNECT проверяется системным каталогом, внешние адреса не опрашиваются.

## 6. Первый запуск C1 — 2026-10-01T12:52:24+03:00
