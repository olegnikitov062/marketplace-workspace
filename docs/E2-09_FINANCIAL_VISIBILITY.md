## Действующая граница SQL и приложения

Точный текущий контракт: tools/access_web_grants.py и isolation_web_contract.py.
Web имеет SELECT перечисленных таблиц, UPDATE SyntheticRecord только value,
ограниченные account/security DML, INSERT Grant/SupportWindow/ExportBinding,
UPDATE отзыва Grant/SupportWindow и Membership.role/state. Изменять идентичность
или область Grant нельзя; изменение права — отзыв и новая строка. У web нет
создания SyntheticRecord, назначения platform_admin, DDL/TEMP/BYPASSRLS,
членства migrator, GRANT OPTION, DELETE истории; DELETE есть у django_session.

В bootstrap_roles.py существует default SELECT для новых public-таблиц migrator.
Поэтому новую таблицу нельзя считать закрытой только из-за отсутствия явного
GRANT в новой миграции: наследуемый ACL необходимо снять и проверить.

27 ENABLE/FORCE RLS таблиц, подписанный точный statement с параметрами,
database/backend/transaction/сроком и серверным контекстом. Произвольный SET
user/org не авторизует SQL. Для SyntheticRecord RLS дополнительно проверяет
живые session/MFA/user/member/Grant/org/cabinet/support; export/change допускают
внутреннее чтение записи, но не создают HTTP view. RLS не скрывает столбцы.

Control plane и Python signer доверенные: подписанный управляющий запрос не
означает, что PostgreSQL самостоятельно проверил пароль, TOTP или делегирование.
Полный захват процесса/ключа/оператора вне этой границы. Новый endpoint
произвольного SQL или его подписи запрещён. Предложение E2-09 эту границу не расширяет.

## Семь предлагаемых бизнес-решений — пока не приняты

1. **Один финансовый блок.** Выручка, себестоимость, расходы, выплаты и все
   зависящие от них показатели закрываются вместе. Независимые категории сейчас
   не вводить: реальных потребителей ещё нет. Если нужны независимые категории,
   сначала определить их состав и запретить все формулы, восстанавливающие
   закрытый вход из открытых выходов; прибыль не может независимо раскрывать
   закрытую себестоимость через известные выручку и расходы.
2. **Никаких автоматических финансовых прав.** Owner, observer и cabinet_user
   получают их только явными Grant. Шаблоны, повышение роли, приглашение,
   восстановление и миграция их не выдают. Observer/cabinet_user могут получить
   отдельно разрешённые view/export/change, но не финансовое manage_access.
3. **Делегирование только владельцем.** Живой owner, свежие пароль+TOTP,
   финансовое manage_access и собственное выдаваемое/отзываемое действие
   в покрывающей области. Самовыдача через HTTP запрещена. Первый финансовый
   администратор — отдельное явное операторское назначение действующему owner
   с подтверждённым MFA; сейчас только подготовка синтетического сценария,
   без назначения реальных людей. Последний владелец защищён прежним правилом;
   нового требования «обязательно оставить финансового администратора» нет.
4. **Два независимых разрешения на операцию.** Новый ресурс synthetic_finance
   в существующем Grant; действия view/export/change/manage_access остаются
   независимыми. Просмотр денег требует synthetic_record/view И
   synthetic_finance/view; финансовый CSV — record/export И finance/export;
   изменение денег — record/change И finance/change. Ни finance/view, ни
   finance/manage_access не даёт остальных действий. Export без view допустим,
   как в E2-07; change без view возвращает только status, без прежних/новых сумм.
5. **Скрытые поля отсутствуют.** При разрешённом обычном чтении и отсутствии
   финансового Grant вернуть обычные данные и finance_visibility=restricted,
   но не финансовые ключи, null, нули, маски или число финансовых строк.
   Признак зависит только от права, не от существования/значений финансов.
   Явный запрос финансового изменения/расчёта без права — общий отказ без
   проверки существования финансовой строки и без деталей данных.
6. **Все зависимые показатели закрыты вместе.** Прибыль, маржа, суммы/средние
   и любые метаданные, зависящие от скрытого блока, не возвращаются.
   Финансовые фильтры/сортировки/группировки в этом объёме отвергаются для всех;
   это проверка отсутствия обхода, не реализация этих возможностей.
7. **Platform_admin и поддержке финансы запрещены.** Запрет чтения, экспорта,
   изменения и делегирования финансов независимо от operator-issued обычного
   Grant и срока support window. Запрет закрепляется и в допустимых сочетаниях
   Grant, и в HTTP/SQL-проверках; оператор БД остаётся отдельной доверенной ролью.

Организационный Grant сохраняет явную семантику E2-07: все кабинеты организации,
включая будущие. Кабинетный — только этот кабинет. Итоговая область операции —
пересечение обычного и финансового Grant, не объединение. Никакого brand scope.
Смена шаблона не должна обходить финансовое делегирование: если затрагиваются
финансовые Grant, менеджер обязан иметь полномочия на их отзыв; иначе отказ
всей операции. Восстановление не расширяет права и не снимает блокировку.

## Ограниченная техническая модель после согласования

Предлагается отдельная синтетическая финансовая запись, связанная 1:1 с
SyntheticRecord, с неизменяемыми organization/cabinet/record и составными FK.
Старый value остаётся неизменным по смыслу. Никакой миграции старых целых в деньги.
Поля — revenue, cost, expenses, payout: Decimal с двумя знаками, одна фиксированная
валюта RUB; конечные ограниченные неотрицательные суммы синтетического сценария.
Это учебное финансовое событие, не бухгалтерская модель маркетплейса. Payout —
отдельная введённая сумма, не обещание равенства расчётной выплате площадки.
Profit=revenue-cost-expenses; margin=profit/revenue при revenue!=0, иначе null
только для авторизованного получателя. Все входы/выходы одного закрытого блока.

**SQL:** отдельная таблица без прямых SELECT/INSERT/UPDATE/DELETE прав web,
включая явный отзыв унаследованного default SELECT в той же транзакции миграции.
FORCE RLS, tenant-FK, неизменяемая связь, запрет удаления истории. Web получает
EXECUTE только фиксированных финансовых read/write функций с типизированными
аргументами, закреплённым search_path и отозванным PUBLIC EXECUTE; без dynamic SQL
и без аргументов «SQL/имя поля/формула». Read обслуживает фиксированную проекцию
записи/небольшого списка, write меняет только перечисленные суммы и не возвращает
значения. Суммы/маржа рассчитываются сервером только из разрешённой проекции.

Каждая функция требует действительный E2-08 signed record-контекст и сама
проверяет live user/session/MFA/org/cabinet, оба Grant и отсутствие platform-role;
control-контекст не разрешает финансовый вызов. Экспортное чтение дополнительно
проверяет permit и закреплённые Grant. Проверка финансового разрешения выполняется
до чтения финансовых строк, вычисления формул или проверки их существования.
SECURITY DEFINER — доверенная фиксированная процедура, а не автоматическая
защита RLS: operator-policy владельца функций сама финансовые права не проверяет.
Поэтому обе проверки внутри функций и тесты реальным web LOGIN обязательны.
Компрометация Python signer/оператора по-прежнему вне модели; SQL web credential
без подписи не читает деньги, а подписанный обычный view без finance Grant тоже
не должен их получить. Это предложение, не уже доказанный SQL-контракт.

**HTTP:** существующие record/list/search/change/export/download вызывают
общую финансовую проекцию. Для change — явный фиксированный финансовый вариант
операции с CSRF и проверкой прав до чтения/валидации против хранимых значений;
обычный value-change не принимает финансовые поля. Без права никакого RETURNING
денег, вычисленного остатка, affected-row count или отражения входа в ошибке.
Для read query-параметры ограничить одинаково на всех синтетических путях.
Нет пользовательского выбора имени столбца или выражения.

Минимальный настоящий потребитель агрегатов: необязательный фиксированный
финансовый итог списка по фактически возвращаемым <=100 записям, с явно
обозначенным scope=returned_records. Только при finance/view. Не изображать
его итогом всего кабинета; UUID-поиск меняет тот же разрешённый срез. При отсутствии
финансового права состав/порядок/количество обычных записей не зависит от денег
или наличия финансовой строки. Отдельная межкабинетная сводка не добавляется.

**Ссылки:** неизменяемая проекция закрепляется при выдаче: обычная либо финансовая,
с конкретными record/export и finance/export Grant. Старые/обычные permit никогда
не приобретают финансовые столбцы после выдачи нового права. Отзыв любого
закреплённого Grant необратимо отзывает permit, даже если существует другое
перекрывающее право. Повторная выдача создаёт новый Grant/permit; revoked_at нельзя
очистить. Изменение области/действия — revoke+create. Существующие каскады
user/member/session/MFA/org/cabinet/record сохранены. Restore — карантин и сверка
актуальных прав, без автоматического оживления старых ссылок.

Каждая операция в одной транзакции: organization → users → права/данные;
повторная живая проверка после блокировок, без кэширования разрешений в сессии.
После завершившегося revoke новый запрос закрыт. Уже выданный до отзыва ответ
из памяти получателя отозвать невозможно; конкуренция проверяется как порядок
транзакций, а не как ретроспективное удаление уже полученных данных.
