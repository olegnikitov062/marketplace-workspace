## Сопоставление с принятой архитектурой

| D1 | Реализация E2-04 |
| --- | --- |
| Личный User без глобального права на данные | `ownership.User`: UUID, username, штатный хеш пароля Django, is_active, archived_at. Нет PermissionsMixin, staff/superuser, глобальной роли, контактов или маршрутов входа. У синтетических пользователей пароль непригоден для входа |
| Organization — отдельная область, не юрлицо | UUID + name + архивная отметка |
| Membership — user/organization/state/template | Единственная строка на пару user/organization; owner, observer, cabinet_user; active/suspended и archived_at. Одинаковый пользователь имеет независимые роли в двух организациях |
| LegalEntity принадлежит организации | UUID, organization FK, условное имя; реальные реквизиты отсутствуют |
| Brand принадлежит организации | UUID, organization FK, имя. Одинаковые названия в разных организациях допустимы и не дают доступа |
| Cabinet принадлежит организации, отдельный от токена | UUID, organization FK, marketplace, имя |
| Версионируемая связь кабинета с юрлицом | `CabinetLegalEntity`: organization, cabinet, legal_entity, observed_from/observed_until. Смена закрывает прежнюю версию и добавляет новую, ссылки остаются. Повтор того же наблюдения идемпотентен |
| SourceConnection принадлежит organization/cabinet | Тип источника, условная идентичность продавца, непрозрачная secret_reference. Значения секретов не хранятся/не читаются; изменение ссылки не создаёт кабинет |
| Составные FK запрещают смешанные организации | Миграция 0002: `(organization_id, cabinet_id)` → Cabinet и `(organization_id, legal_entity_id)` → LegalEntity. Проверяются также bulk_create/update, минующие clean |
| Архивирование сохраняет историю | archived_at, ORM PROTECT и запрет ORM delete; PostgreSQL запрещает DELETE всех ownership-таблиц, смену organization_id и перезапись исторической привязки. Архив не удаляет связи |

`membership_role` каждый раз читает действующее членство, состояние пользователя и организации. `can_manage_memberships` различает owner и остальные шаблоны согласно D1; это модельная проверка, не API управления членствами. Нет кабинетного чтения, экспорта, финансовых разрешений или выдачи grant. Технический пользователь не получает обхода организации. Стандартные таблицы auth/permissions создаются миграциями Django, но пользователь не связан с ними и RBAC на их основе не включён.

Связи истории создаются сервисом `observe_legal_entity`: транзакция и блокировка строки кабинета сериализуют смены на PostgreSQL. Сохраняется момент наблюдения UTC, без придуманной исторической даты юридического владения. Предыдущая версия может быть только закрыта; закрытая дата и идентичность связи не переписываются. Есть уникальность одной незакрытой версии и положительная длительность закрытого интервала. Архивирование не закрывает/не пересчитывает приписывание автоматически.

## Неоднозначности и границы

- D3 и полная матрица прав ещё не приняты. Роли — предусмотренные D1 шаблоны, а active/suspended — минимальные технические состояния; приглашения/восстановление/блокировка сессий здесь отсутствуют. Не добавлены правила «последнего владельца», число владельцев или автоматическая передача владения.
- Историческая фактическая дата перехода к юрлицу неизвестна: записывается только наблюдение. Интерфейс ретроспективного исправления, согласование спорной истории и отчётная атрибуция относятся к будущим задачам. Прикладная запись истории должна идти через сервис; защита PostgreSQL от смешанных FK и перезаписи истории не заменяет будущие ограничения доступа к SQL и RLS.
- D1 не задаёт здесь связь Brand → Cabinet/LegalEntity, уникальность имени/продавца, список marketplace/source_type или карточки товаров. Они не придуманы; Brand пока самостоятельный справочник организации.
- Архивирование — сохранение строки и ссылок, без удаления/каскадного архивирования потомков. Архив организации закрывает модельную проверку членства; история доступна для технического восстановления. Публичных предметных API нет.
- Вход, приглашения, полноценный RBAC/Grant, RLS, UI, worker, разрешённые источники и секретное хранилище не реализованы. docs/SYSTEM_DESIGN.md прочитан как предложение, дополнительный объём из него не взят.

## Восстановление и безопасный локальный откат

Миграция 0002 обратима: снимает только добавленные составные FK/триггеры/функции, строки остаются. На beta обратный шаг временно снимает защиту, поэтому допустим только в закрытой тестовой среде с немедленным forward/проверкой. Миграция 0001 → zero удаляет ownership-таблицы и их данные: это не способ восстановления заполненной БД. Для заполненной beta сохранять схему/данные и возвращать совместимый код либо восстанавливать проверенный dump в новую отдельную БД после отдельного решения. Не восстанавливать поверх живой БД и не удалять data/config/secrets.

Исходные локальные копии четырёх существующих файлов: `.change-backups/2026-09-30/E2-04/{settings.py,SYSTEM_PLAN.md,CHANGELOG.md,RUNBOOK.md}`. Промежуточные версии новых файлов — `iteration-1/`. Точный перечень файлов и SHA-256 результата — `manifest.json` там же. Перед откатом сравнить текущие hashes и сохранить позднюю работу; вернуть только изменения E2-04 в settings/плане/RUNBOOK. CHANGELOG не сокращать, добавить отмену. Новые исходники/документ/протокол удалять только по манифесту, при совпадении и отсутствии поздних правок; сначала убрать ссылки/регистрацию приложения. Резервные копии сохранять до завершения отката. Не использовать git reset/clean, общий prune или рекурсивное удаление корня.
