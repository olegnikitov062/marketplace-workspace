## 2. Решения Олега и оставшиеся уточнения

В текущем ответе Олег выбрал обязательный MFA для владельцев и добровольный для остальных; согласовал правила подключения/замены и узкие страницы. Направление восстановления и раздельного хранения ключа принято. По срокам выбрано «Изменить параметры» без новых значений: прежние предложения **не приняты**. Оператор/способ проверки личности и место/хранитель копии ключа пока не определены. Численные параметры TOTP, лимитов и количества кодов ниже также остаются предложениями.

| Решение | Предложение для согласования |
| --- | --- |
| Обязательность — согласовано | Владельцам обязательно, остальным добровольно. Owner хотя бы одной активной организации должен завершить MFA; требование заново проверяется по актуальному членству при каждом защищённом запросе. До подключения обязательного фактора — только ограниченное подключение/выход. Для добровольно включившего MFA пароль также не обходит второй фактор. Снятие роли owner не отключает уже подключённый фактор |
| Подключение | Свежий пароль, затем подтверждение корректным TOTP. Неподтверждённый секрет не считается фактором |
| Замена | Свежий пароль и старый TOTP либо резервный код; новый фактор подтверждается до замены старого. Подтверждение атомарно отзывает прежние сессии, старый фактор и старые коды |
| Отключение | Для обязательного MFA запрещено; восстановление переводит в ограниченное повторное подключение, а не выключает требование. Если выбран добровольный режим — пароль + текущий фактор, отзыв всех сессий/ссылок |
| Выход | Обычный выход — текущая сессия; отдельные операции «отозвать выбранную» и «выйти везде». Идентификатор в списке не является ключом cookie |
| Смена/восстановление пароля, блокировка, восстановление/замена MFA | Все сессии и незавершённые входы, повторные подтверждения и ранее выданные ссылки. Смена пароля не снимает MFA. После обычной смены пароля также новый вход |
| Сроки — Олег запросил изменение, значения ожидаются | Отклонённое первоначальное предложение: максимум 8 часов; простой 30 минут; промежуточный вход 5 минут; повторное подтверждение 5 минут. Новые значения не заданы. Матрица отзыва/remember-device также запрошена отдельно, поскольку ответ относился к общему вопросу |
| TOTP | Штатный алгоритм, 6 цифр/30 секунд, окно ±1 шаг, контроль last_t и запрет повторного использования; точное время в тестах фиксируется, автоматическое расширение окна запрещено |
| Попытки | Предварительно 5 за 15 минут на аккаунт/операцию и 30 на peer/операцию плюс штатная задержка библиотеки. Общие атомарные счётчики PostgreSQL, включая промежуточный вход; обновление cookie не сбрасывает лимит |
| Резервные коды | 10 случайных высокоэнтропийных кодов; однократная выдача пользователю, в БД только стойкие проверочные значения; повторная генерация аннулирует весь прежний набор. Ни вывода в отчёт, ни доставки email |
| Потеря TOTP владельцем | Пароль + резервный код открывают только ограниченное восстановление/подключение нового TOTP; нет автоматического расширения доступа. Полный доступ после подтверждения нового фактора и нового входа |
| Потеря всех факторов | Требуются имя/роль доверенного оператора, заранее определённый независимый способ подтверждения личности и порядок одобрения. Оператор выдаёт короткое одноразовое разрешение на повторное подключение, не входит как владелец, не выключает MFA, не меняет пароль/членства/права. Неподтверждённый запрос по email недостаточен. Альтернатива — явно не поддерживать этот сценарий, сохранив незакрытый критерий |
| Ключ TOTP | Отдельный файл вне БД/Git, отдельные ключи beta/production; read-only mount только необходимым процессам. Независимая защищённая копия у Олега; нужны место хранения, хранитель и полномочия на восстановление. Не создавать ключи до разрешения |
| Минимальный интерфейс | Только backend-страницы подключения/входа/повторного подтверждения/восстановления и собственных сессий. Без React UI приложения, внешних CDN и публичной публикации |

Операторское восстановление потребует ограниченного журнала событий безопасности в E2-06 (тип, время, внутренние ссылки на участников/запрос, результат, без секретов). Это не общий аудит E2-11. В публичный отчёт не включать идентификаторы реальных лиц. Операция выпуска разрешения не должна быть доступна SQL-роли web; его потребление отдельно ограничивается неизменяемой привязкой аккаунта и одноразовым состоянием. Выбор конкретных полномочий оператора отложен до ответа; migrator не объявляется автоматически доверенным оператором личности.

## 5. Почему стандартного подключения пакета недостаточно

Исходник django-two-factor-auth **1.18.1** явно использует TOTPDeviceForm/TOTPDevice, StaticDevice/StaticToken. Штатный мастер сохраняет ключ как в extra_data, так и в session для QR. Django DB sessions подписаны, но не шифруют содержимое. Простого шифрования конечной таблицы TOTP недостаточно. Штатные `key`/`token` django-otp являются CharField; StaticToken сравнивается непосредственно и удаляется после успеха. Нельзя назвать такие резервные коды хешированными.

Предлагаемый узкий вариант для отдельного выбора: сохранить библиотечный мастер и OTP-проверку; адаптировать устройства/формы/хранилище через точки расширения, используя cryptography для AEAD/Fernet и штатные Django password hashers для резервных кодов. Не менять установленный пакет, не monkeypatch моделей, не реализовывать собственный TOTP/криптоалгоритм. Точную возможность интеграции encrypted device с конкретным release нужно подтвердить локальным исследованием после согласования зависимостей: registry расширяется, но SetupView/backup flow имеют жёсткие ссылки на штатные модели. До доказательства такой интеграции это **предложение**, не готовое решение.

Если безопасная узкая адаптация требует замены существенной части MFA, остановить этот вариант и вынести архитектурное решение Олегу. Молчаливого перехода на другую библиотеку или собственной SPA-MFA нет. Временные секреты, введённые TOTP/коды и wizard validated data не должны появиться открытым текстом в session_data, БД, логах или dump. Без ключа/при неверном ключе — отказ, а не отключение MFA. SQL exception logging и тестовые failure repr также входят в проверку утечек.

Точки источника: [wizard/QR/storage релиза](https://github.com/jazzband/django-two-factor-auth/blob/1.18.1/two_factor/views/core.py), [формы](https://github.com/jazzband/django-two-factor-auth/blob/1.18.1/two_factor/forms.py), [registry](https://github.com/jazzband/django-two-factor-auth/blob/1.18.1/two_factor/plugins/registry.py), [поддерживаемые Device extension](https://django-otp-official.readthedocs.io/en/stable/extend.html), [транзакционная OTP-проверка](https://django-otp-official.readthedocs.io/en/stable/auth.html).

## 6. Ограниченный объём и стыки

1. **Сессии.** Отдельный реестр User → Django session с безопасным публичным ID, сроками и состоянием отзыва; версия безопасности аккаунта для массового отзыва. Middleware проверяет актуальное состояние до защищённого обработчика. Старые сессии без реестра/MFA закрываются при переходе; смена cookie/повторный save параллельного запроса не воскрешают отозванную сессию. Состояние login/MFA связывается с текущей версией пароля/аккаунта и имеет отдельный короткий срок. Блокировка и отзыв сериализуются с выдачей полноценной сессии.
2. **Права.** Повторно использовать действующую проверку Membership/owner на каждом запросе. Проверить смену owner→observer и suspended при сохранённой cookie на настоящем действии приглашения. Изменения членств в сценарии выполняет ограниченный тестом оператор, web не получает UPDATE role/state. Не вводить Grant/кабинетную матрицу. Гарантия — запросы после commit отзыва; уже отправленные байты невозможно отозвать. Гонки защищённых мутаций проверять через общий порядок блокировок и финальную проверку перед эффектом.
3. **Синтетическая ссылка.** Предлагается реальная серверная запись разрешения на скачивание, связанная с пользователем/организацией/сессией/сроком и состоянием отзыва, случайный непрозрачный токен с безопасным проверочным значением. При скачивании обязательны действующая полная сессия того же пользователя и свежая проверка членства/состояния ссылки. Реальный HTTP-ответ отдаёт только фиксированное синтетическое содержимое; доступ другой организации, анонимный доступ, отозванная ссылка и прежняя cookie отказывают. Нет статической раздачи файла или bearer-only доступа. Выпуск доступен только закрытой синтетической проверке; публичного API выпуска/прав экспорта ещё нет. После отзыва ссылки её нельзя оживить повторной выдачей членства. Это действующий механизм авторизации/отзыва ссылки, **не рабочий экспорт**.
4. **Зависимости критериев.** В E2-06 можно подтвердить текущие owner/member-права и отзыв конкретной синтетической ссылки. Независимое право export, cabinet/brand scope и защита реальных файлов/кэша/worker остаются E2-07/E2-08/E5-07/E2-16. Пока они отсутствуют, общий критерий экспорта не закрывать без согласованного сужения приёмки; строку критерия плана не переписывать. Проверка двух организаций на этих auth/link endpoints не доказывает RLS.
5. **Восстановление.** Парольное восстановление сохраняет MFA; неактивный/архивный/pending аккаунт не получает обход. Операторское разрешение ограничено неизменяемым user, имеет срок/одноразовое использование и журнал. Ни повторное приглашение, ни восстановление не расширяют организации/область/роль. Восстановление из старой БД может вернуть использованные коды/отозванные сессии: после аварийного restore нужен отдельный режим запрета старых сессий/ссылок/кодов и контролируемое повторное подключение, а не автоматический рабочий запуск восстановленной копии.

Ни один из этих новых механизмов ещё не реализован и не проверен. Новые model/DDL/API имена фиксируются после выбора решения; список не выдаётся за исполненный SQL-контракт.

## 7. Приёмочная матрица новой реализации

| Группа | Необходимое доказательство |
| --- | --- |
| Подключение | Неправильный код не подтверждает; правильный подтверждает; код подключения нельзя использовать повторно для входа; два конкурирующих подтверждения не создают два активных фактора |
| TOTP | Верный/неверный/вне окна/повторный код; замороженное время на границе окна; два независимых PostgreSQL соединения — один успешный потребитель |
| Лимиты | Неверные попытки сохраняются и при отказе/rollback бизнес-операции; общие лимиты между процессами/сессиями; конкурентный первый счётчик; отсутствие обхода через смену device/session |
| Неполный вход | После пароля без MFA все защищённые endpoints закрыты, включая старый login и invitation; просроченный/отозванный login challenge не завершается |
| Резервные коды | Hash-only, однократный показ; неверный/старый/использованный набор; два конкурентных запроса — один успех; пароль/блокировка всё равно проверяются |
| Владелец | Согласованный путь при потере TOTP; отдельно потеря всех факторов, если согласована; полномочия/область до и после равны; оператор не получает сессию владельца; неизвестный/blocked/archive/pending отказывают |
| Сессии | Текущая/выбранная/все; отказ чужого session ID; абсолютный срок/простой; пароль/reset/block/MFA; гонки входа/отзыва/сохранения session; старые cookie не оживают |
| Права и ссылки | Одна cookie до/после committed смены роли/отзыва членства; 200 до и отказ после отзыва ссылки; смена организации, чужой пользователь, повторное назначение членства, срок; операторские обновления не расширяют web SQL |
| HTTP/утечки | CSRF на всех изменяющих запросах, GET не мутирует; no-store для MFA, отсутствие секретов в URL/логах/failure traces/session_data/DB dump; locmem и только example.invalid; реальные отправки запрещены |
| SQL | Реальный ограниченный LOGIN, точные table/column grants, grant/revoke/reapply, отрицательные DDL/role/membership/recovery-issue/audit-change проверки; без RESET ROLE эскалации |
| Миграции/restore | План/sqlmigrate/drift; forward/reverse/forward только отдельной схемы; dump/restore в новую БД, корректный/неверный/отсутствующий отдельный ключ; поведенческая проверка и отсутствие возрождения старых полномочий |

Полный новый PostgreSQL suite должен пройти без пропусков значимых сценариев. SQLite проверяет только доступные локальные свойства и не подтверждает concurrency/ACL/SQL guards. Прошлые 63 теста E2-05 не считаются новыми тестами. Все значения тестовых паролей/кодов/ключей/ссылок генерируются/используются внутри проверки и не выводятся. Проверка утечек выдаёт только pass/fail/count, без найденного значения.

## 8. Серверный план для последующего отдельного разрешения

Сейчас не исполнять, включая SSH. Это проверяемая последовательность и границы, **не готовый разрешённый запуск**: точные команды, column ACL, digest образа и опубликованный SHA добавляются после реализации/локальных проверок. Без них разрешение на выполнение не запрашивается.

### S0 — подготовка ревизии и отдельного образа

После выбора политики и разрешения локальных пакетов: зафиксировать зависимости/hashes, code/migrations/tests/SQL plan/deploy overlays и локальные коммиты Oleg. Олег проверяет и делает push. Затем отдельно разрешается серверный Git pull --ff-only опубликованной beta и проверка чистоты/SHA. Никаких архивов или ручного редактирования source. Новый read-only worktree внутри `beta/app/releases/<SHA>`. Отдельная разрешённая сборка с закреплёнными wheels/lock, immutable image/digest; не pip install в работающем web. Старый образ/worktree/overlay сохраняются.

### S1 — изолированные PostgreSQL-тесты и восстановление

- До создания сверить own project labels, main web/DB images/mounts/ID/StartedAt, migrations и ресурсы; зафиксировать отсутствие изменений после. Работа только в `postgres-test`/`marketplace-beta-test-private`, без host ports/ingress. Не запускать старые probes.
- Новые кандидаты имён: `mw_beta_test_e2_06_suite`, `mw_beta_test_e2_06_web`, `mw_beta_test_e2_06_recovery`, `mw_beta_test_e2_06_restore`; limited LOGIN только `mw_beta_test_e2_06_web`. Их доступность пока неизвестна. При любом совпадении — остановка, без reuse/drop; новые имена согласовать, не подбирать автоматически. Все исторические C1/A/B/restore сохраняются.
- Test runner владеет только своей схемой; web LOGIN без superuser/CREATEDB/CREATEROLE/REPLICATION/BYPASSRLS/наследования, CONNECT только своей БД. Новый SQL-контракт должен перечислить точные SELECT/INSERT/UPDATE колонки реестра/устройств/счётчиков/хешей/ссылок. Не выдавать новые права на роли/членства, выпуск операторского разрешения, изменение журнала, DDL/default blanket grants. Проверить настоящий session_user=current_user и существующие E2-05 guards.
- Отдельный синтетический test key в защищённом test-only файле; ключ основной beta не использовать. Не печатать secret/ENV/compose resolved config. Утверждённый порядок доставки копии ключа проверяется отдельно от dump; БД/backup без ключа не должны раскрывать TOTP.
- Suite и HTTP/CSRF/конкурентные тесты под PostgreSQL 17; отдельная проверка limited LOGIN и grant/revoke/reapply. Секрет роли только в памяти; завершение проверяет NOLOGIN/PASSWORD NULL. Обрыв процесса требует readback и отдельного отключения только собственной тестовой роли.
- Синтетический seed только в новой recovery БД. Новый `beta/backups/test/e2-06-<run-id>.dump`, 0600, без перезаписи; ACL snapshot отдельно без credential values. Restore `--exit-on-error --no-owner --no-acl` только в новую пустую restore БД, без PUBLIC CONNECT. Сверить миграции/строки/guards/поведение в памяти; отдельно применить/проверить её узкие ACL. Секретные строки/fingerprints секретов не выводить. Dump/БД/ключи сохранять до отдельного решения; раздельная копия ключа остаётся защищённой.

### S2 — основной web, отдельное разрешение после S1

Проверить именно протестированные SHA/lock/image digest. Новый закрытый backup `beta/backups/database/e2-06-before-<run-id>.dump` и ACL snapshot, восстановление в новую `mw_beta_test_e2_06_main_before` (имя также проверить), без перезаписи живой БД. До применения сверить текущие counts/миграции — пустота E2-05 не предполагается сохранённой. Сохранить действующую конфигурацию/overlay отдельно, без вывода секретов. Создание основного beta TOTP key и его независимой копии требует отдельного разрешения на точные пути/хранителя.

Просмотр migrate --plan/sqlmigrate и безопасного compatibility/rollback плана; миграции только migrator, затем транзакционный guarded ACL delta. Обновление только web с новым образом и фиксированным Git source/новым проверенным overlay, никаких base-only up. Web получает только собственные runtime secrets, не operator/migrator. Проверить SQL-контракт, реальный HTTP/MFA/CSRF/runtime readiness, отсутствие портов/чужих сетей, неизменность обоих PostgreSQL и teardown одноразовых процессов. Реальные аккаунты/доставка/Caddy не включаются.

### Откат

До включения E2-06 основной web остаётся на E2-05. После включения MFA простой возврат E2-05 создаст вход без второго фактора: **такой откат недопустим**. Нужен заранее реализованный и проверенный maintenance/deny-auth вариант либо исправление вперёд. При неудаче закрыть новые входы/защищённые маршруты или остановить только собственный beta web, сохранив данные, ключи и контейнеры PostgreSQL; конкретный способ входит в разрешение S2. E2-05 overlay/worktree нужен для воспроизводимости, но сам по себе не безопасный fallback для аккаунтов с MFA.

Отзыв только новых grants — после остановки их потребителей и проверки отсутствия позднего расширения ACL; не запускать старый E2-05 revoke, ожидающий другую схему прав. Данные MFA не удалять через zero; restore только в отдельную новую БД, без возрождения старых сессий/кодов. Общие reset/clean/prune/down -v запрещены. Локально сравнить hashes и позднюю работу, применить только обратный diff подготовки, журнал дополнить отменой. Копии двух изменяемых документов: `.change-backups/2026-10-01/E2-06-preparation-143251/`; новый этот файл удалять только при совпадении manifest hash и отсутствии поздней работы/ссылок.
