# E2-06: подготовка передачи зашифрованной копии ключа

02.10.2026, Europe/Moscow. Разрешена **подготовка передачи**, сама передача не выполнялась. Файл нового пароля уже создан по последующему прямому запросу Олега. Создание нового envelope, чтение основного ключа, получение ciphertext и его запись в локальное назначение требуют отдельного согласования этого конкретного этапа. Telegram агентом не используется. Этот план независим от разрешённого синтетического browser R2.

## Предлагаемый результат

Олег уточнил: сохранить в Telegram оба отдельных файла — зашифрованную копию ключа beta и файл пароля. Он подтвердил этот выбор после объяснения, что доступ к одному Telegram даст доступ и к ключу; это явное изменение прежнего решения о раздельном хранении. По его запросу создан закрытый локальный файл нового случайного пароля; зашифрованная копия с этим паролем ещё не создана. В будущей операции Олег вводит этот пароль скрыто в своей интерактивной сессии. Существующие серверные key/envelope/passphrase не удаляются и не передаются в чат. Реальный аварийный секрет владельца — другой секрет, его выдача сюда не входит.

Чтобы не пересылать ранее созданный серверный пароль, предлагается новый envelope того же основного TOTP key с **новым паролем, известным Олегу**. Runtime key, БД, web, MFA-факторы и права не меняются. Используется существующий `tools.mfa_key_backup wrap`: Scrypt/Fernet, getpass, новый файл O_EXCL, 0600. Новые библиотеки не нужны. Старую копию S2 сохранить для отката.

## K1 — закрытая серверная обёртка с вводом Олега

1. После отдельного разрешения сверить текущую основную beta, RO key mount и metadata сохранённых S2 envelope/passphrase; содержимое не выводить. Проверить существующий image и опубликованный неизменный crypto/backup код. Новый каталог должен отсутствовать; его создание и выставление 0700/UID10001 — единственные подготовительные записи.
2. Олег открывает свою интерактивную SSH-сессию. Агент не записывает её экран, stdin/stdout, transcript или историю введённого пароля. Если интерактивное окно недоступно, этот шаг откладывается, пароль не передаётся через чат/ENV/аргументы.
3. В одноразовом контейнере существующего образа разрешены только RO source, RO beta key и RW новый output-каталог. Network none, logging none, read-only filesystem, UID10001, cap-drop ALL, no-new-privileges, 256MiB/0.25CPU, без БД и web. Пример команды ниже выполняет именно Олег в интерактивной сессии; переменная release задаётся заранее проверенным опубликованным Git release с неизменённым backup-кодом.

```sh
docker run --rm -it --pull never --network none --read-only \
  --log-driver none --user 10001:10001 --cap-drop ALL \
  --security-opt no-new-privileges:true --memory 256m --cpus 0.25 --pids-limit 64 \
  --mount "type=bind,src=$release/backend,dst=/workspace,readonly" \
  --mount type=bind,src=/home/adm_user/marketplace-workspace/beta/config/secrets/mfa_encryption_key,dst=/run/private/key,readonly \
  --mount type=bind,src=/home/adm_user/marketplace-workspace/beta/backups/database/e2-06-owner-key-envelope-20261002,dst=/run/private/output \
  sha256:86f9cac63025d6c6119d2f7e0b232004b3ebfe98a82800a672bef73fdd1fbe72 \
  python -c 'import getpass,os,runpy,warnings; assert os.isatty(0) and os.isatty(1); warnings.simplefilter("error",getpass.GetPassWarning); runpy.run_module("tools.mfa_key_backup",run_name="__main__")' \
  wrap --input /run/private/key --output /run/private/output/envelope.json
```

Олег берёт новый пароль из подготовленного закрытого файла и вводит его дважды скрыто. Старый серверный пароль S2 не используется для нового envelope. При ошибке getpass/TTY операция завершается, ввод с echo не допускается. Пароль не сохраняется серверным процессом; новый файл содержит только password-encrypted envelope. Нового plaintext TOTP key не создаётся. Код backup не меняется, запрет plaintext restore на Windows сохраняется.

## K2 — получение и проверка копии

Получить **только новый envelope** по SSH в приватный локальный процесс; SSH не выводить в журнал. Сохранить целевой файл эксклюзивно после проверки ACL, без перезаписи. Источник ограничен указанным envelope размером не более 4096 bytes; если серверные права не позволяют прямое чтение, разрешить одноразовый контейнер с RO mount только envelope, network none/logging none/UID10001 — его stdout направляется исключительно в приватный приёмник, не в вывод инструмента. Основной ключ и серверный старый пароль не скачиваются.

Проверить побайтовое совпадение зашифрованного источника и локального файла в памяти; наружу только boolean. Не печатать ciphertext, salt, пароль, ключ или fingerprints ключа. Затем Олег запускает локально в обычном интерактивном терминале, из backend:

```powershell
& .venv/Scripts/python.exe -m tools.check_mfa_key_envelope --input 'C:/Users/krolo/Documents/marketplace-recovery/beta/e2-06-key-envelope-20261002.json'
```

Инструмент отказывается от неинтерактивного ввода/вывода и fallback getpass с echo. Он проверяет обычный файл ≤4096 bytes, аутентичность envelope и формат Fernet key, ничего не пишет и выводит только результат. Успех подтверждает расшифрование данной копии введённым паролем; принадлежность основному key устанавливается созданием envelope из проверенного RO runtime key и проверкой передачи. Это не проверка восстановления БД из dump и не изменение runtime ключа.

## K3 — независимое хранение и приёмка

По новому явному решению Олег самостоятельно загружает оба отдельных файла в Telegram. Агент ничего не отправляет от его имени. Совместное хранение не защищает ключ при компрометации этого Telegram; согласованный риск зафиксирован, не объявляется раздельным каналом хранения. Для подтверждения независимой от VPS копии Олег скачивает файлы обратно в новые приватные имена, после чего проверяются совпадение ciphertext и локальная проверка расшифрования с его скрытым вводом пароля из скачанной копии. Само наличие файла на VPS или первоначальная загрузка на ноутбук не объявляются проверенной копией в Telegram.

Критерий передачи закрывается только после фактического получения независимого envelope и успешной проверки скачанных обратно файлов Олегом. Файл нового пароля уже существует локально, но пока ни с каким envelope не связан; это не выполненная передача ключа. Пока K1/K2/K3 не выполнены, в плане сохраняется «На проверке». Основная beta остаётся в том же состоянии; аккаунты, роли, сессии и реальные owner proofs не создаются.

## Проверки подготовки и откат

Три локальных теста новой утилиты прошли: верный/неверный пароль и повреждённый синтетический envelope без plaintext output/new files; отказ неинтерактивного запуска до пароля; отказ fallback getpass с echo до проверки. Только синтетические ключи, пароль в памяти, без БД/SSH/реальных секретов. Windows ACL каталогов и созданного файла пароля проверены фактически; настоящий интерактивный терминал Олега и фактическая передача envelope ещё не проверены.

При отказе не менять основной key или старые S2 backups. Сохранить новый частичный output и остановить одноразовый процесс; не перезаписывать/регенерировать файл автоматически. Удаление частичного server/local envelope — отдельное решение после проверки точного пути, неизменности, отсутствия использования и сохранения нужного доказательства; общего удаления каталогов нет. Откат runtime не нужен, поскольку он не менялся. Потеря пароля нового envelope не отключает MFA и не даёт аварийного входа; исходный ключ/старые закрытые копии остаются до отдельного решения о хранении.
