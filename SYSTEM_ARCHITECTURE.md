Для аналитики предлагается собственное имя `analytics.158-160-30-90.sslip.io` (кандидат, не созданный/проверенный адрес). При изменении фактического IP имя меняется соответственно. Схема имён с вложенным IP поддерживается [sslip.io](https://nip.io/), HTTPS и проксирование — [Caddy](https://caddyserver.com/docs/automatic-https). DNS/выдача сертификата/доступность именно этого имени проверяются перед разрешённым выпуском; сейчас на сервер и целевой адрес обращений не было. Временное имя зависит от внешнего DNS-сервиса и IP; переход на собственный домен позже потребует обновить hostname/ALLOWED_HOSTS/CSRF origin и проверить вход.

Размещение: отдельный каталог приложения на сервере (предлагаемый `/home/adm_user/marketplace-workspace`, проверить перед созданием), отдельный Compose project `marketplace-workspace`, собственные web/worker/PostgreSQL, секреты и volumes. Уточнение Олега: на сервере новая система занимает **одну верхнюю папку `/home/adm_user/marketplace-workspace/`**; отдельные соседние папки под код, deploy, логи, БД или резервные копии не создаются. Структура каждого окружения внутри `production/` и `beta/`: `app/frontend/` и `app/backend/` — код интерфейса и сервера, `deploy/` — Compose и конфигурация входа приложения, `config/` — закрытая конфигурация/секреты вне Git, `data/postgres/` — данные собственной БД, `data/exports/` — временные выгрузки, `logs/` — файловые журналы, `backups/` — временные локальные копии перед переносом во внешнее хранилище. Рабочие данные подключаются bind mounts к этим путям; обновление кода не заменяет data/config/backups. Секреты не включаются в архив кода и журналы. Перед созданием проверяются точный путь, свободное место и права; рекурсивное удаление общей папки не является способом обновления или отката. PostgreSQL-данные копируются штатным способом резервирования, не простым копированием работающего каталога.

Одна папка относится к принадлежащим приложению файлам: Docker Engine хранит образы/служебные журналы в своих системных каталогах, а существующий общий Caddy и обязательная внешняя копия остаются вне неё. Подключение нового маршрута потребует согласованной правки общего Caddy; текущие папки FBS не переносятся и не меняются этим решением. Это уточнение документа D1, не выполненное размещение на сервере.
Сеть PostgreSQL доступна только своим процессам; PostgreSQL не публикуется наружу, общая БД WB/FBS не используется для собственного хранения. Для чтения WB используется согласованное least-privilege подключение, не подключение всех новых контейнеров к широкой сети Airflow.

Вход: существующий Caddy получает отдельный блок hostname и проксирует только web через выделенную внешнюю Docker-сеть входа, общую исключительно для proxy и web. Worker/БД к этой сети не подключаются, web к внутренней сети FBS не подключается. Это проектируемая схема: текущая локальная конфигурация Caddy подключена к fbs_net, поэтому потребуется отдельное согласованное изменение его сетей/конфигурации. Второй proxy с теми же host-портами 80/443 конфликтует и не предусмотрен. Изменение общей точки входа затрагивает FBS: перед выпуском нужны копия конфигурации, проверка Caddy, способ reload/отката и контроль доступа к FBS до/после; перезапуск приложения FBS не предполагается. Сейчас эти изменения не выполняются.

Контейнеры/БД/тома новой системы независимы по жизненному циклу; лимиты CPU/RAM, ротация логов и свободный диск защищают соседние приложения. При этом сервер и Caddy — общие точки отказа, а контейнерная изоляция не обеспечивает отдельный SLA. Перед выпуском отдельно разрешить чтение ресурсов/нагрузки/конфигурации облачного сервера; при нехватке сначала вынести на решение увеличение ресурсов или отдельный VPS. Уточнение места не принимает весь D1, не разрешает установку, обращения на прод или реализацию E2-02.


### 2.2. Расширяемость под много сценариев и частые изменения

Уточнение Олега 30.09.2026: сложные рабочие сценарии точно появятся, потребуется много правок. Ограничивать основу только простым отчётом недостаточно. Поэтому UI/API разделяются сразу, но объём реализации пилота остаётся прежним; редакторы, массовые операции и другие модули сейчас не создаются.

Frontend — модули по процессам (reports/products/operations, позже finance/planning и другие), общие компоненты таблиц/фильтров/форм/состояний ошибок; backend — предметные модули со своими сервисами/проверками, без бизнес-формул в React или HTTP views. Компоненты и состояние разделяются по ответственности, как описано в [React](https://react.dev/learn/thinking-in-react); само наличие React не гарантирует удобства изменений. Общие компоненты выделяются по реальному повторению, не строится заранее универсальный конструктор всех неизвестных Sheets.

Контракт: /api/v1, OpenAPI, генерируемые TypeScript-типы и проверка совместимости схемы; генерация типов не заменяет runtime validation на сервере. Деньги передаются decimal-строками, ID строками; набор данных включает область/период/зону/report_revision. UI-правка не меняет формулу: источник и определение показателя остаются серверными. Изменение контракта сначала совместимое/добавочное, несовместимое — с новой версией и согласованным выпуском. API, worker и frontend в пилоте выпускаются одной проверенной версией, независимые релизы не обещаются автоматически.

Вход остаётся Django session + CSRF под одним origin; в пилоте стандартные Django/MFA-страницы входа могут обслуживаться backend, а рабочие экраны — React. Отдельная реализация MFA для SPA не пишется самодельно. Caddy раздаёт frontend/dist (собранный артефакт внутри единой папки) и направляет /api, /auth и при необходимости /admin только в backend web; fallback SPA не перехватывает API/экспорт. Админка не предназначена для обычных пользователей. Работа dev frontend с cookie/CSRF проверяется через локальный proxy. Права на списки/объекты/поля/изменения проверяет сервер; [DRF](https://www.django-rest-framework.org/api-guide/permissions/) не выполняет всю предметную изоляцию автоматически. Ключи query cache включают организацию/кабинет/фильтры/ревизию; при смене области/отзыве прав старый кэш очищается, чужие данные не появляются из браузерной памяти.

Для будущих ручных изменений заранее предусмотрены отдельные команды предметной области, server validation, revision/optimistic concurrency, idempotency key и audit. При конфликте — явный ответ и сравнение версий, а не молчаливое перетирание. Массовое действие будет иметь предварительный просмотр, зафиксированный состав/версии, лимит, фоновое задание и результаты по объектам; полная/частичная атомарность определяется конкретным процессом, для внешних операций — отдельный D7. Эти контракты реализуются только в предусмотренных задачах E2/E8, не в E2-01.

Серверная фильтрация/сортировка/пагинация, отдельный итог всего набора, виртуализация больших таблиц по измерению; не передавать всю историю в браузер. UI-state (черновики/выделение) отделяется от server-state (TanStack Query); таблицы — TanStack Table как кандидат без привязки к платному grid. Конкретные требования вставки диапазонов/редактирования ячеек/формул сначала проверить по доступному процессу. Полная совместимость с Google Sheets не обещается.

Проверки изменений: API-контракт, предметные инварианты и tenant isolation; UI-состояния/черновики/конфликты, браузерный сценарий затронутого процесса. Миграции совместимы с текущим выпуском и имеют проверяемый откат. Новые процессы добавляются отдельными модулями без переписывания ядра происхождения/прав. Это уменьшает область правок, но не исключает будущих переработок после появления ещё неизвестных требований/таблиц. Дополнительная стоимость — сборка frontend, обновление JS-зависимостей и проверка API/UI; бесплатного по сопровождению расширения нет.

Выпуск: локальная разработка/автоматические проверки → та же зафиксированная сборка и миграции в beta → проверка затронутых сценариев, изоляции, контракта и восстановления → отдельное разрешение на production → резервная копия/проверенные миграции и перенос той же сборки. Рабочая БД не заменяется beta-БД. Фиксируются hash/версия сборки и результаты; изменение после проверки требует повторной проверки затронутых сценариев. Откат кода и откат данных рассматриваются отдельно, несовместимые/необратимые миграции заранее согласуются.

Beta и production делят физический сервер/Caddy: нужны лимиты CPU/RAM/диска/логов, ограничение фоновых заданий и проверка ресурсоёмкости до размещения. Нагрузочные испытания, способные мешать FBS/ETL/production, проводятся отдельно, не на общей машине без специального согласования. Если текущего сервера недостаточно, сначала решение об увеличении ресурсов/отдельной beta-машине. Приёмка beta не является разрешением выпуска на прод.

## 4. Организации, владение и права

| Объект | Предлагаемая модель |
| --- | --- |
| User | Личный аккаунт; не содержит глобального права на все данные |
| Organization | Собственная область изоляции, UUID; не отождествляется с юрлицом |
| Membership | user + organization + состояние + шаблон роли; один пользователь имеет разные полномочия в разных организациях |
| LegalEntity | UUID + organization; фактические реквизиты вводятся только в разрешённой защищённой среде |
| Cabinet | UUID + organization + marketplace; отдельная сущность от токена. Связь с юрлицом версионируется при изменении, история не пересчитывается молча |
| SourceConnection | organization/cabinet + тип источника + идентичность продавца + ссылка на секрет; ротация токена не создаёт новый кабинет |
| Brand | Справочник организации и связи с карточками; название бренда не определяет право доступа или владельца |
| Grant | Ресурс + действие + область организации/кабинета; позже подтверждённая область бренда. Ничего не выдано → запрет |

Шаблоны: владелец организации управляет членствами; наблюдатель читает явно разрешённые кабинеты; пользователь кабинета читает свою область. Просмотр, экспорт, изменение ручных данных, управление доступом и просмотр финансовых полей — отдельные разрешения; просмотр не даёт экспорт. Финансовые поля скрываются на сервере, не только в UI. Реальные люди и матрица D3 сейчас не определяются. Технический superuser не используется как повседневный аккаунт и не подменяет владельца организации.

Все tenant-таблицы содержат organization_id, кабинетные — также cabinet_id; составные FK запрещают ссылку на объект другой организации. Сервис доступа проверяет активное членство и grant на каждом запросе/экспорте и повторно при выполнении пользовательского задания. PostgreSQL RLS — второй барьер: контекст пользователя/организации задаётся SET LOCAL в транзакции после серверной проверки; отсутствующий контекст закрывает доступ, пул не сохраняет чужой контекст. Web-роль не владелец таблиц, не superuser/BYPASSRLS; FORCE RLS для защищаемых таблиц. Миграционная роль отделена. Worker имеет узкие полномочия для конкретного подключения, а не общий обход изоляции. RLS по организации не заменяет проверку кабинетных grant и полей. Прямого клиентского подключения к БД нет.

Проверки будущего E2: подмена UUID в URL, скачивание/истёкшая ссылка, чужой кабинет внутри той же организации, смешанные FK, отзыв членства/экспорта при активной сессии, worker и пул после переключения организации. Полная матрица и тесты выполняются в соответствующих задачах, сейчас описан дизайн.

## 5. Вход и восстановление

Личные логин/пароль, TOTP, одноразовые восстановительные коды, серверная HttpOnly/Secure/SameSite-cookie и CSRF-защита. Пароли хешируются штатным поддерживаемым механизмом Django; значения и TOTP-секреты не логируются. TOTP-секреты шифруются отдельным ключом вне БД; копия ключа шифрования TOTP хранится отдельно и проверяется в E2-06, общая проверка резервирования относится к E2-15/D4. Уточнение 01.10.2026 по согласованию с Олегом: прежняя ссылка на E2-12 ошибочна, эта задача посвящена правилам API; ключ шифрования отличается от одноразовых восстановительных кодов пользователя. Нет публичной регистрации, общих аккаунтов и браузерных WB-токенов.

Приглашение: одноразовый случайный токен с hash в БД, сроком и областью членства; истечение/повтор/блокировка проверяются сервером. В этапах 2–5 доставка в локальный приёмник, без реальных email. Рабочая доставка и восстановление по email выбираются позже с D7, нового платного провайдера сейчас не требуется. Потеря второго фактора владельца: восстановительный код либо документированная администраторская процедура с проверкой личности и аудитом; не отключение MFA по публичному запросу.

Блокировка отзывает сессии и ссылки; смена прав действует сразу через живую проверку, не роль из старой cookie. Нужны ограничение попыток входа/TOTP/восстановления и журнал отказов; минимально отдельная таблица счётчиков с атомарными обновлениями в PostgreSQL, без Redis. Срок сессии/приглашения и процедура владельца — предварительная конфигурация E2-05/06, не уже реализованный механизм.

## 6. Чтение источников без изменения загрузчиков

Основной адаптер читает supplier_sales и разрешённые поля dict_product_ul, wb_tokens, каталога/размеров. Не читать секретные значения источника, если достаточно псевдонимов/ключей соответствия. Существующий FastAPI не выбран основным: преобразования/группировки и непроверенный live контракт могут скрыть исходное зерно.

Нужна отдельная роль источника SELECT только на необходимые таблицы/колонки; не использовать прежнюю мощную роль приложения. Создание роли/сетевого доступа на проде — отдельное разрешение, не действие E2-01. Если такую роль пока нельзя выдать, вход адаптера — разрешённый защищённый экспорт, подготовленный отдельно; не обход через superuser.

Будущее чтение: READ ONLY, statement_timeout 15 s, lock_timeout 2 s, один читатель, фиксированный день пилота; keyset-порции ориентировочно 1000 строк, без OFFSET по всей истории. Дневной план сейчас показывает последовательное чтение: LIMIT не гарантирует дешёвый запрос. Сначала согласовать ограниченный запрос/EXPLAIN и измерить; при таймауте остановиться, предложить экспорт/реплику отдельно, не увеличивать нагрузку и не создавать индекс в рабочей БД. Каталог и операции читаются в согласованном транзакционном снимке, где возможно; время каждого источника сохраняется отдельно.

Контрольный адаптер WB Statistics/seller-info относится к конкретному cabinet_id/подключению; токен только на сервере. Новые GET, получение полного набора и расписание требуют нового разрешённого объёма. Сейчас сетевые обращения к WB, БД и Airflow не выполнялись. Одновременные прямые API-загрузки и старые загрузчики требуют учёта лимитов, поэтому прямое WB API в пилоте — контроль, а не второй бесконтрольный загрузчик.

Будущая политика обновлений: повтор фиксированного дня и перекрывающееся окно изменений, плюс отдельная ручная сверка старого периода. Точный интервал/частота/глубина определяются E3-07/08 по ограничениям источника и разрешённой нагрузке; измерение одной коррекции не доказывает, что все изменения укладываются в 7/42 дня. Отсутствие строки в ответе не означает удаление/ноль без доказанного полного ответа.

## 7. Происхождение, версии и воспроизводимый отчёт

Предлагаемые логические сущности, не миграции и не готовая схема:

| Сущность | Сохраняемая информация |
| --- | --- |
| SourceRead | UUID, источник/подключение/заявленная область, параметры периода, начало/конец чтения UTC, статус/полнота, версия адаптера/контракта, число строк, hash набора |
| RawRecord | SourceRead, исходный ключ/поля, hash payload; money сохраняется также исходным строковым представлением. Allowlist исключает секреты и ненужные персональные поля |
| OperationVersion | organization/cabinet, тип источника, srid + saleID как TEXT для Statistics sales, исходное/нормализованное время события, lastChangeDate, время наблюдения, номер версии, raw-ссылка, суммы Decimal/NUMERIC, статус качества |
| Observation | Связь повторного чтения с уже известной версией; одинаковый payload не создаёт новую смысловую версию, но факт нового чтения сохраняется |
| Attribution | Способ привязки области: explicit_api / current_mapping / verified_snapshot / unresolved; версия справочника, доказательство и время наблюдения; исторический период действия только если подтверждён |
| ReportRevision | UUID отчёта, период/зона/область, конкретный набор версий и справочников, версия определения показателей, контрольные суммы/ограничения |
| Reconciliation | Две ревизии источников, количества/ключи/суммы, отличие, причина или открытый вопрос, время контроля |

Ключ операции — `(organization_id, cabinet_id, source_type, srid, saleID)`, версия различается содержимым и provenance. Возврат — отдельное событие, не перезапись продажи с тем же srid. Пустой ключ/неизвестный формат — карантин, не молчаливый пропуск. Позднее наблюдение с более старым lastChangeDate не становится автоматически текущим. При одинаковом lastChangeDate и разном payload сохраняются обе версии и конфликт. «Последняя в БД» и «последняя в API» — две независимые линии источника; правило выбора зафиксировано в ревизии, не скрыто.

У source read из смешанной БД область может быть «общая», а cabinet attribution строки — предположение текущего моста. Доказанная область ответа API принадлежит подключению кабинета, но сама по себе не доказывает юридического собственника товара в прошлом. Для WB-02/29.09 кабинетный состав подтверждён совпадением ключей с конкретным GET. Для остальных исторических строк текущий dict_product_ul не превращается в доказательство: несопоставленные/сомнительные строки остаются в защищённом карантине общей зоны загрузки, без публикации в чужом кабинете. Разница до/после отбора отражается счётчиком. История владения создаётся с момента наблюдения; valid_from не выдумывается задним числом.

Товар: `(cabinet_id, nm_id)`; вариант: `(cabinet_id, nm_id, chrt_id)`; barcode — TEXT и многозначная связь с вариантом, не PK. Операция с известным nmID входит в товарную сумму и при неоднозначном размере; размер остаётся unresolved. JOIN не размножает денежную строку. Операции без товарной связи сохраняются отдельной группой «не определено», чтобы детализация плюс эта группа сходилась со сводкой. Ручные замены barcode в будущем — отдельные версионированные соответствия, исходный barcode сохраняется.

Для денег — Decimal в Python и NUMERIC в PostgreSQL, исходная точность не округляется до агрегации; в UI RUB с двумя знаками, правило округления записывается. Если БД уже сохранила double precision, её исходную точность нельзя восстановить выдуманными цифрами; сохраняется полученное представление и ограничение. Исходные даты TEXT сохраняются; naive date/lastChangeDate Statistics разбираются по подтверждённой Europe/Moscow и переводятся в UTC, календарный день отчёта остаётся Московским. lastChangeDate не заменяет loaded_at; время чтения не выдаётся за неизвестное время загрузки в WB БД.

Пример обязательного поведения пилота:

- Ревизия БД: 215 операций, forPay 650128,15 ₽; API-ревизия: те же 215 ключей, forPay 649965,91 ₽.
- Разница API−БД −162,24 ₽ в одной операции; lastChangeDate 29.09 22:16:14 → 30.09 11:08:42 МСК. Сохраняются обе наблюдаемые версии, не выполняется ручная правка рабочей БД.
- В каждой ревизии totalPrice 1731966,00 ₽, finishedPrice 617268,40 ₽, 10 возвратов. Историческая сводка открывается со своими версиями до уровня операций; нельзя смешать сводку БД с детализацией API.
- Значения отмечены операционными/предварительными, не окончательной выплатой. Неполная финансовая история — «данных недостаточно», не нулевые расходы.

В артефактах E1 нет полного payload операций; D1 описывает ожидаемую проверку, не утверждает наличие восстановимых raw-версий уже прошедшего чтения. Потребуется новое разрешённое получение либо контрольная синтетическая пара версий для технического теста; сегодняшнее API не обязано повторить старые суммы.

## 8. Фоновые задания, резервирование и развитие

Очередь PostgreSQL: pending/running/succeeded/failed/cancelled, lease, attempts, next_run_at, idempotency key, кабинет и источник. Захват транзакционно через блокировку строки, lease восстанавливается после остановки; долгие запросы выполняются вне транзакции захвата. Результат/версия и checkpoint записываются атомарно, частичный набор не публикуется успешным. Пользовательский экспорт перепроверяет grant перед формированием и выдачей. Планировщик отдельного worker ставит только согласованные задания; текущий Airflow не меняется.

Начальные кандидаты эксплуатации: web readiness отдельно от свежести источника; счётчики ошибок/полноты/конфликтов/неопределённых связей; логи без payload/секретов. Резервировать собственную БД, raw, конфигурацию без секретов и отдельно ключи восстановления. Ежедневная копия вне VPS и пробное восстановление на тестовой среде перед выпуском. Предварительный RPO 24 часа/RTO 4 часа — предложение для D4, не гарантия; ручные данные требуют отдельного согласования меньшего RPO/PITR. Никакой автоматической очистки истории до принятия срока хранения. Источники не изменяются при откате новой системы.

Расширение идёт отдельными модулями и source contracts: финансы с подтверждёнными документами/историей себестоимости; остатки со временем снимка; ручные планы/комментарии отдельными фактами; Ozon и остальные площадки после своего обследования. Не проектировать универсальную EAV-таблицу для всех неизвестных Sheets. Общими остаются область доступа, provenance, версии, задания и аудит; предметные поля добавляются миграциями под проверенный процесс.
